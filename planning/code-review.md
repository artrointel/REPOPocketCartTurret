# 코드 검토 — 2026-10-20

게임에서는 호스트가 고정된다는 전제로 검토했다.

## 정리 및 수정

- 전역 `Sound.Play` 진단 패치, 오디오·렌더러·탐지·첫 발 로그, 5초 주기 상태 출력, 프리팹 프로브와 F8 검사, 폐기한 사운드 후보 문서를 제거했다. 플러그인 로드·오류 로그와 최초 요청한 Debug 스테이지 장비 스폰은 유지했다.
- 기존 지뢰의 절대 수명 5초는 반복 가림이나 긴 조준 대기에서 발사 전에 경고음을 없앨 수 있었다. 제어기가 대기 중 수명을 갱신하도록 수정했다. 관리가 끊긴 지뢰에만 5초 정리 제한을 적용한다.
- 경고 지뢰를 잡는 경로와 별개로 인벤토리에 넣는 `RPC_RequestEquip`도 차단했다. 일반 구매 지뢰에는 적용하지 않는다.
- 늦게 접속한 참가자가 생성된 지뢰만 받고 설치 상태·사용 금지를 놓치지 않도록 두 초기 RPC를 버퍼에 보관한다. 설치된 Photon의 `RemoveInstantiatedGO`에서 객체 제거 시 생성 캐시 및 `OpCleanRpcBuffer` 호출을 확인했다.

## 남은 위험 및 검증 시나리오

| 우선순위 | 시나리오 | 코드 검토 결과와 필요한 확인 |
| --- | --- | --- |
| 중간 | 순정 참가자가 경고 중 무기 바로 위를 잡거나 인벤토리 키를 누름 | 지뢰의 호스트 충돌·잡기 승인·장착 요청은 막지만, 순정 참가자의 로컬 콜라이더는 남아 있다. 무기와 지뢰가 같은 위치이므로 로컬 선택/조준을 가릴 가능성이 있다. 실제 순정 클라이언트로 상호작용 검증이 필요하다. |
| 중간 | 총구가 벽이나 카트 내부에 겹침 | 사선 검사는 `Physics.RaycastAll`에 의존하며 시작점의 겹침을 별도로 검사하지 않는다. 비정상 겹침 자세에서 오발/탐지 실패가 없는지 물리 플레이 검증이 필요하다. 코드만으로 재현을 확정하지 않았다. |
| 낮음 | 여러 터렛과 많은 적이 동시에 존재함 | 매 프레임 후보를 순회하고 `RaycastAll` 결과 배열을 할당한다. 규모가 커지면 GC·프레임 지연 가능성이 있으나 성능 측정은 하지 않았다. |

## 검증 범위

Debug·Release 컴파일, 순수 탐지·타이밍·조준 규칙 검사, 빌드 산출물의 패치/진단 코드 제거 검사, 설치된 게임 DLL의 계약 확인을 수행한다. 늦은 접속·순정 클라이언트 상호작용의 수정 후 실제 멀티플레이 검증은 별도로 필요하다. 세부 절차는 [수동 검증 계획](test-plan.md)을 따른다.
